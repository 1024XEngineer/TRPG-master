# Issue #415：离散时间模型的作者态契约

规则引擎的时间是**离散**的：不流逝、不按分钟累加、不能落在两个已声明的点之间。
房间只能从 `current_point_id` 跳到时间线上的下一个点。本文档写的是模组作者与
解析侧（#399 系）必须遵循的约定；规范性定义在
`contracts/module_v3.py` 的 `ModuleTimePolicySpec` / `TimePointSpec` 上，这里
只解释为什么。

## 1. 时间线是一个按小时升序声明的环

`default_points` 按 `hour_of_day` 升序声明，`order` 就是环上的位置。起点由
`initial_state.start_time_point_id` 指定，可以落在环上**任意一点**；越过末点时
回卷到首点并 `day_index + 1`。

跨午夜的夜晚因此不需要按时序声明，也不需要放宽升序校验：

```
按小时升序声明 00/02/18/20/22，起点指定 hour_18

  D0 18:00 → D0 20:00 → D0 22:00 → D1 00:00 → D1 02:00 → D1 18:00
                                    ^^^^^^ 越过末点回卷，day_index + 1
```

注意声明顺序是 `00/02/18/20/22` 而不是走查顺序 `18/20/22/00/02`——后者本身不是
升序，写进 `default_points` 会被 `validate_points` 直接拒绝。夜晚的时序由「起点
落在哪」表达，不由声明顺序表达。

`ModuleTimePolicySpec.validate_points` 的「`hour_of_day` 必须随 `order` 严格
递增」是**声明顺序**约束，不是表达力约束。它保证 `order` 与环上位置一致，别的
什么都不保证。

## 2. `default_points` 是完整覆盖

解析侧按模组的实际叙事粒度生成**整条**时间线，不与默认四点合并：

| 原文里的时间信息 | 解析侧生成 |
|---|---|
| 完全没有 | 使用默认四点（00 / 06 / 12 / 18） |
| 只有 day / night 粒度 | 两个点，缺省 06 / 18，原文短措辞挂到各点 `label` |
| 出现具体小时 | 生成或复用对应小时点，构成完整点列表 |

机械合并会制造两类真实缺陷：多出来的点是额外的推进边界（玩家被迫多按几次
「下一个时间点」），而且同一条 night 规则会在一天里命中两次——只有昼夜之分的
模组尤其明显。

## 3. 三层分离：id / time_segment / label

以前这三件事挤在 `time_of_day` 一个值上。

| 层 | 字段 | 谁写 | 谁读 |
|---|---|---|---|
| 精确身份 | `id` / `hour_of_day` | 模组 | 引擎排序、`time_point_is` 谓词 |
| **规则语义** | `time_segment` 四段枚举 | 模组逐点声明，缺省由小时推导 | 通用规则层 `time_of_day_is` |
| 玩家措辞 | `label` 自由文本 | 模组 | 仅投影，**规则不得读** |

缺省推导（`segment_at_hour` / `default_label_for`）：

| 小时 | canonical segment | 缺省 label |
|---|---|---|
| 00–05 | `late_night` | 凌晨 |
| 06–11 | `morning` | 上午 |
| 12–17 | `afternoon` | 下午 |
| 18–23 | `evening` | 晚上 |

模组可逐点覆盖。05:00 声明 `time_segment="morning"`、`label="黎明"` 之后，规则
按 morning/day 判断，玩家只看到「黎明」。旧的 `time_of_day_at_hour` 把 06–18
硬编码成 day，这样的模组会被判成 night——那正是它被替换掉的原因。

### 为什么两个字段都要留着

**`label` 不能替代枚举。** label 是自由文本。通用规则若匹配「晚上」这个显示
字符串，模组把它改写成「深夜」就失效了，等于把模组的表达习惯塞进通用契约——
#401 §1 明令禁止的方向。

**枚举也不能替代 `label`。** 通用 CoC 7e 规则（夜间侦查减值、只在夜里出现的
生物）必须对所有 CoC 7e 模组成立。它问得出「现在是不是夜里」，问不出「现在是
不是 `h02`」，后者是模组私有 id。

`time_of_day_is` 因此保留，`day` / `night` 作为**查询别名**继续可用：

- `day` = {`morning`, `afternoon`}
- `night` = {`evening`, `late_night`}

查询传四段值时精确匹配，传 `day` / `night` 时按集合匹配（`matches_time_query`）。
别名**只在查询里存在**，不作为运行态存储值：存 `night` 就再也分不出凌晨和晚上。

## 4. 运行时定时任务与临时点

模组声明的默认点是环上固定的几刻。定时任务要落在「12 点和 18 点之间的 15:00」
这种作者没声明过的时刻上，靠的是插一个**一次性 occurrence**，再让下一跳解析把
它混进默认点按绝对时刻重排。

三条不变量：

1. **任务绑 occurrence，不绑时刻。** 同日同小时的多个任务共享一个 occurrence，
   所以取消其中一个既不动其他任务，也不动那个点；只有该点所有任务都取消且尚未
   进入时才移除它。
2. **目标恰好是默认点时不建临时 occurrence。** 建了就等于同一刻来两次。
3. **目标不能晚于 `terminal_point`。** 越界任务永远不会到期，留着就是一条静默
   失效的剧情线，所以在创建时以 `invalid_time_task_target` 拒绝；恰好等于终点时
   允许绑定。

任务 id 从 `rule_id + task_key + bindings` 推导而不是随机生成：重试才不会排出
第二个一模一样的任务，`cancel_time_task` 也才定位得到——它手上只有 key 和
bindings。

### 单次发布

进入一个有任务等着的时刻时，「把任务标记 completed」和「发 `time.task_due`」
出自同一个 `ApplyResult`，由引擎在同一次事务里提交。重试、断线与进程恢复都从
已经 completed 的状态重跑，结算返回空，第二条事件不会存在——单次发布因此不依赖
任何调用方自觉。

同一刻的多个任务按 `priority` 再按 `task_id` 稳定排序，否则恢复重放出来的世界
和第一次跑出来的不一样。

### 玩家边界

`time.task_due` 是 hidden 事件，是规则管线的信号而不是玩家投影。隐藏任务的
存在、来源与后果都不进 PlayerView：玩家在临时点上只看到按 canonical segment
解析出的安全 label（临时点没有 `TimePointSpec`），看不到精确小时，也看不到
occurrence id。

## 5. 就近绑定归解析侧

「玩家夜间会听到……」应当绑定具体 point id 还是使用粗粒度时间谓词，是原文语义
问题，只有解析侧答得了。`label` 只负责显示，不承载任何规则语义。
