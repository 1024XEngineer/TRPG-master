**1. 本次决策**

按本轮用户要求，近期继续使用现有主持链路，独立交付以下三项能力，不等待 #421 完成。

| 项目 | 本期做法 | 后续 Agent 可复用的部分 |

本期不新建持续决策循环、上下文检索系统、第三套叙事服务或中间反馈状态机。现有 `rule_once`、ActionPlan 和恢复路径共同使用修正后的叙事能力。

**3. 开场原文：解析与发布**

`ModuleContentV3` 顶层使用两个可选字段：

```python
opening_text: str | None = None
opening_key_facts: tuple[str, ...] = ()
```

含义是“该发布版本、当前默认起始路径中，允许向全体玩家朗读的模组开场原文”。这是正式开局用的故事文本，独立于 `background`、`presentation.player_intro_pages` 和地点的 `player_visible_description`。近期只支持当前共同起点所对应的一份公共开场；私人 HO 和可选择的多开场不在此处扩展。

旧数据允许缺省，新增或重新发布的正式内置模组要求提供非空正文。语义校验可对旧内容缺省给出提示，发布门禁检查本次更新的模组；不能把已有会话因缺少新字段直接判为不可加载。

解析任务需要明确增加以下产物要求：

- 从原文选择完整的玩家开场段落，逐段复制，保留顺序、对白、段落和事实细节；只允许必要的文档抽取排版规范化。
- 同步提取 `opening_key_facts`，保留任务、线索来源、数量/单位、时间、条件和行动限制，记录与原文相同的来源。非空清单必须有原文；省去重复氛围描写，不能把未知改成确定。
- 识别并分离夹在导入中的 KP 指导、后续分支答案和隐藏信息。选择正确的公开原文片段，不把整章守秘人资料一起作为开场。
- 原文涉及初始人物、物品或已知事实时，核对其与实体定义、起始地点、初始已知信息及初始持有关系一致。例如原文已经交付某件可携带物品，应在模组初始数据中有对应表达。
- 在现有 `module-content-provenance.json` sidecar 中增加 `opening_text` 的来源记录：源文件及页码或段落索引。来源信息留在解析审阅资料中。
- 提取不全、来源缺失、公共开场与起始状态冲突时，记录为解析内容缺口，回到内容整理环节解决；运行时模型不承担补写原文的职责。

本期已更新有原始来源的三个内置模组：《追书人》《银之锁》《幸福蛙蛙村》。《常暗之厢》因原始 PDF 缺失保留旧版兼容，明确记录为待补内容。有构建脚本的同步修改脚本及产物；直接维护 JSON 的保留清楚的出处。比如《幸福蛙蛙村》现有构建脚本已经有按 DOCX 段落索引记录来源的方法，可复用。原始来源无法取得的模组要明确记为待补齐，不能把现有简介冒充原文后宣称验收完成。

发布兼容采用以下口径：

- 保留 `content_schema_version=3`，同步 Pydantic 契约、导出 JSON Schema、解析规范和发布检查。
- 可选字段缺省时，不让规范化 JSON 凭空多出 `opening_text: null` 或 `opening_key_facts: []`，避免已有同版本内容的相等比较因新增默认字段失败；用旧 JSON 的序列化兼容用例固定此行为。
- 增加原文或关键事实清单的模组必须提升 `version`，同步 `BuiltinModuleSpec`、构建脚本和测试引用；新增不可变 `ModuleVersion`，不覆盖旧版本记录。
- 新房间使用新模组版本；已有会话继续读取已绑定版本。已发布的 `game-opening` 直接回放，不重新生成。

[内置模组加载器](../trpg-backend/app/service/builtin_module_loader.py) 比较同一版本的完整规范化内容，内容变化会拒绝覆盖。上述版本更新与代码应作为同一批发布；不需要为单个 JSON 内容字段新增数据库列。

回退运行行为时可以切到原文 template 模式，但已发布新模组、保存新证据后，读取端仍必须认识新字段和证据类型。不能直接回滚到拒绝这些字段的旧程序；版本兼容读取应保留。

**4. 开场生成：把模型任务改成原文适配**

近期复用 `SessionViewApplication.generate_opening → ContextAssembler.for_opening → OpeningNarrator`，不增加模型调用阶段。

开场原文及关键事实清单从会话所绑定的 `runtime.module_content` 读取，与起始人物/场景投影保持同一会话、同一版本。将原文作为显式参数送入 `for_opening`，扩展 `OpeningNarrationContext`；避免把它塞进每个普通行动都携带的 `PlayerView.background`。

开场输入以原文和关键事实为主体。`OpeningNarrationContext.to_prompt_dict()` 统一用于提供方请求和输入长度日志：去掉内部 actor/scene ID、空值和默认空字段；有原文时去掉整模组背景及单人履历。保留公开场景名称、描述、当前有效时间、非空现场细节，以及参与者的姓名、公开职业、公开状态和身体限制，避免机械删掉必要现场约束。缺少原文的旧模组保留原有背景入口。

提示词允许按原意重排、合并句段、改写对白和略去重复修饰；必须清楚交代关键事实及其数量、时间、条件，不能新增调查线索或把未知写成确定。单人且允许第二人称时自然称“你”，无需强制点名；多人或 named_actor 模式仍要求完整姓名与清楚的叙事主体。人物身份不必被写成逐人职业感知或附加名单。

本期保留现有开场输出协议和一次生成、预算内一次重试。取消整段原文逐字正则和 `source_coverage` 重试要求；语义完整的改写不会再仅因标点、句序或用词变化被拒绝。结构、开场空事实 ID/空行动建议、协议残留、多人姓名与主体校验继续运行，耗尽后仍使用完整原文兜底。

`opening_key_facts` 是生成提醒，不是模型自报的覆盖证明。当前程序不自动证明每项关键事实都已讲出，也不会因为事实遗漏而自动触发重试；遗漏与新增内容通过少量真实样例人工核查。按用户确认的取舍，不新建运行时审核模型或面向单一模组的词句匹配规则。未来 #421 可以复用原文、清单与安全场景输入。

原文中的事实要在模组发布时与初始状态对齐。开场生成器只做表达，不执行规则效果、不补发物品或新增线索状态。

开场降级规则需要一起修改：

| 情况 | 返回方式 |
| --- | --- |
| 有原文，模型正常 | 基于原文和关键事实自然改写的正文 |
| 有原文，模型超时、失败或校验耗尽 | 完整原文，加一小段由真实人物资料组成的在场介绍 |
| 有原文，配置为 template | 使用相同的原文输出方式 |
| 旧模组版本没有原文 | 保留旧版本可运行的兼容开场，日志标识 `legacy_missing_opening`；不把它计入新能力验收 |

原文兜底应保留作者朗读体的第二人称，并在这一确定性分支将其视为对在场调查员的称呼。校验应能确认正文确由已审核原文及固定人物介绍组成。这是源文本分支的明确边界：不再因为原文出现“你”而整段丢掉，也不把这一处理扩大到模型自由生成的多人行动叙事。

人物轻改成功的输出仍遵守多人行动主体要求。原文兜底优先确保完整性，暂不保证每个原句都逐一改成角色名；这是本方案选择的降级取舍。

继续使用现有 `game-opening` 身份、先落库后广播及刷新去重机制；客户端仍收到普通叙事文本。

**5. 新增结果：现在补通，后续供 Agent 选用**

新增结果的修复以 [#513](https://github.com/1024XEngineer/TRPG-master/issues/513) 和 [#446](https://github.com/1024XEngineer/TRPG-master/issues/446) 为归属。[#514](https://github.com/1024XEngineer/TRPG-master/issues/514#issuecomment-5462208697) 已合并入 #513，不能据其关闭状态跳过实现。

在现有 `NarrationEvidence` 增加 `kind="information_revealed"`，继续使用 `ref`、`subject_id`、`subject_name`、`description`、`required_in_narration`，不另造与之平行的新结果清单。

映射口径：

| 证据字段 | 来源 |
| --- | --- |
| `ref` | 本次已提交的 `information.revealed.event_id` |
| `subject_id` | `information_id` |
| `subject_name` | 该信息的玩家可见标题 |
| `description` | 玩家安全投影里的完整 `player_content` |
| `required_in_narration` | 满足下述公开、新增及表达条件时为 true |

判定条件应在已有事件投影处完成：事件已提交；本次反馈的受众有权知道；相对于此次执行前的同受众知识确为新增；执行后仍允许向该受众公开。当前 `narration.push` 是全房间广播，因此新增必写证据只收共同公开的结果；不能把行动者个人视图里的私有事实一起广播。

同时尊重已有 `Information.presentation.channels`：配置包含 `narration` 的新增公共信息必写；显式仅面向 journal/handout 的资料保持其配置。本期不设置“只写前 N 条”的截断规则，避免把遗漏改成确定性的丢弃。

不能只判断事件类型：当前重复 `reveal_information` 仍可能发出事件。需要比较执行前后公开知识，并按事件顺序去重。同一事实在同一批次重复揭示只表达一次；旧事实仍可作为背景，但不再次标为新发现。个人已知变为全队公开时，对公共受众仍算新增。

这段投影以现有 `_narration_evidence(runtime, new_state, events, player_id, actor_id)` 为入口。必要时抽出小型纯函数，输入已提交事件、前后状态及投影受众，输出现有证据契约；函数不依赖 ActionPlan、队列表或 WebSocket。当前 orchestrator 继续按已完成步骤聚合，后续 Agent 可以复用同一投影来获取每次工具执行的结果。

2026-09-11 根据大厅进入日志调整为与开场一致的策略：**完整 `player_content` 作为事实底稿，允许自然重排、合并及改述，提示保留人物关系、数量、时间、否定与条件。** 不再以逐字匹配衡量语义完整性。该规则作用于通用信息揭示，包括进入场景时自动公开的地图资料，不新增场景专用链路。

模型通过既有 `claimed_evidence_refs` 声明正文使用的信息来源，服务端校验引用范围及必写项的声明；原文确实完整出现时，仍可自动补上漏填的引用。实体发现继续要求公开名称或别名。引用声明不能证明正文语义完整，与开场一样由提示和少量真实样本核对事实覆盖，不增加语义判定模型。原文匹配仅用于恢复引用及限定来源文字的样式豁免，不用于拒绝正常改述。

推荐提示词补充：

```text
本次 narration_evidence 中 information_revealed 且 required_in_narration=true
的 description，是这次处理刚刚确认并应当告知玩家的事实。
按原意自然融入当前反馈，保留数量、时间、否定和条件，不必逐字引用。
将正文实际表达的事实 ref 放入 claimed_evidence_refs；申报本身不能代替正文。
不要只写标题，不要把它留给信息面板，也不要用历史已知线索代替。
其它 known_information 是背景，不自动表示本次有了新发现。
```

既有公开性校验与内容投影继续生效。未来 Agent 可以选择相关背景和表达时机，服务器仍负责确认所选事实已经提交、受众正确，以及本次应表达的结果没有在传递时消失。

**6. 所有输出路径共同保留新增结果**

不能只在最后一次错误恰好是 `required_evidence_missing` 时补结果。当前第二次错误若变成 `atmosphere_repeat` 等类别，就会走只输出少数状态或通用完成句的兜底。

现有 `_narrate` 保持最多两次模型尝试。模型成功时检查来源引用、实体名称、已提交的抵达结果及既有安全边界；不宣称自动证明改述后的语义完整性。缺少必写声明、结构错误或其他校验失败时仍重试，耗尽后由确定性兜底保留事实原文。

确定性文本按证据种类生成：信息揭示使用完整 `description`，实体发现沿用公开名称及原有描述兜底（多人下仍跳过不符合人称的实体描述），位置变化说明已抵达的地点，标准状态变化使用已有结果。可以按因果顺序组成短段；不要给信息套用“辨认出某实体”的模板。未通过安全校验的模型句子不因补结果而重新混入最终输出。

原文保留要与现有文本校验衔接：已公开信息正文自身可能带单数“你”或引号。服务器可以依据本次合法证据的完整正文匹配出来源片段，在这些片段内保留作者对玩家的称呼和原文引号；相关人称、NPC 引语及氛围检查仍作用于其余模型生成的文字。来源片段必须由服务器匹配确认，模型自报来源不能获得豁免，受众及证据合法性也始终检查。自然改述的文字按普通叙事校验。

句级降级会移除必写信息及抵达结果的模型引用声明后重新校验：剩余正文需要完整保留来源原文及目的地名称，否则转到现有原文兜底。这样避免“事实句被删掉，但引用还在”被当作有效反馈。

有必要澄清或后续步骤失败时，先保留此前已确认的结果，再交代尚未完成的部分；`kind=clarification` 不能成为吞掉已完成结果的理由。无新增结果的普通回应仍可简短。

关键回归包括：第一次漏报信息、第二次触发其它校验；删掉违规小句时恰好删到了新增结果；复合行动前一步揭示线索、后一步失败。三种情况最后都必须保留已经提交且应公开的信息。

本方案不接管 [#515](https://github.com/1024XEngineer/TRPG-master/issues/515) 的完整定向修补设计，但会修复与信息丢失直接相关的兜底收束。#513 还包含死亡状态表达：实施时应把《幸福蛙蛙村》的死亡统一为现有标准 `consciousness=dead`，同步初始值、条件和效果引用，避免只补信息后角色状态仍按活人处理。只有两个断点都完成并验证，才能按完整场景关闭 #513。

**7. 抵达场景：提示词为主，保留必要的代码修正**

不增加专用“首次进场 Agent”或独立叙事服务。继续由现有 ActionPlanNarrator 使用当前 `PlayerView.scene`、可见实体、公开状态和出口组织现场。

先做两处小范围修正：

- `committed_results_from_events` 识别当前的 `travel.resolved/destination_id`，生成 `CommittedResult(kind=location)`。兼容 `location.entered/location_id`；`travel.interrupted` 只在发生实际移动时记录 `current_location_id`，不能把请求的目标当成已抵达。
- 给环境去重传入由权威抵达结果及当前场景确认的场景变化条件。换场时放开“时间词 + 光线/窗景类别重叠”这类粗规则，保留对整句照抄的检查；普通同地点连续行动仍按已有去重原则处理。上一段叙事继续作为历史提供，不能因换场就丢失人物和行动连续性。

场景变化条件来自已完成效果，不来自玩家说“去某处”、规划里的 travel 步骤或模型自报。使用已有旅行 `path[0]` 确认出发地点；指向当前地点的无实际移动不启动抵达介绍；中间旅行已完成但最终还在澄清时，仍应明确最终真实位置。

提示词建议收敛为以下分支：

```text
本次有已经确认的场景抵达时，自然交代抵达后的现场，并引用对应 location 结果。
地点可以自然称呼，不要求逐字复制目的地全称。
依据当前场景描述、公开可见的人物及物件、公开状态、可感知出口和路径，
让玩家理解周围有什么，以及能对哪些对象采取行动。
以公开场景描述为底稿，将人物、物件、出入口和新增事实自然组织成连贯段落，
避免“周围可见 / 可见出口”清单及重复播报；已知入口不等于获准进入。
首次展示该地点时可以用足够篇幅建立空间和氛围。
已有介绍的地点再次进入时，结合历史自然缩短，重点写变化与当前在场情况。

新地点也有相同时段、光线或天气时，可以正常表达；不要复述出发地的画面。
普通同地点行动优先讲行动结果，不重复完整介绍环境。
具体信息以当前可见资料为准；缺少的关键空间结构不自行补成既定事实。
```

本期不要求新建严格的“该场景是否已向所有玩家完整介绍过”账本。先保证实际抵达能充分介绍现场，重复篇幅由提示词结合现有历史处理。这一阶段不会保证所有长历史下的再次进入都准确压缩。

如果后续需要严格区分首次访问与再次访问，应使用执行前已有的地点知识 `visited`。最终视图中的 `visited=true` 已经被本次移动更新，不能用它反推“此前来过”。届时由当前持有前后快照的代码投影这一事实，或供 #421 选用；无需建立第二套访问状态。

提示词方案的素材前提也要验收：对《幸福蛙蛙村》等一句话地点，结合已有可见实体和出口能说明的部分直接使用；原文有、结构化数据没有的公开布置补进现有 `player_visible_description` 或对应实体描述，并保留来源。无需为了这次修复给每个地点再建一套 read-aloud 系统。

**8. 与 #421 的交接方式**

| 能力 | 当前调用方 | #421 方向下的调用方 |
| --- | --- | --- |
| 读取开场原文并按人物适配 | `SessionViewApplication` | 开局职责仍可独立保留；Agent 按需调用相同能力 |
| 从本次提交中提取安全结果 | 现有裁决服务与步骤汇总 | 每次规则工具执行后的结果投影 |
| 选择历史、人物、背景材料 | 现有固定上下文装配 | Agent 按本次叙事需要选择相关材料 |
| 保留应表达的新增结果 | 当前一次行动的终局反馈 | 每次已确认后果的即时反馈 |
| 判定哪些结果已反馈 | 现有最终叙事落库与请求幂等 | 将本次使用的证据引用绑定到已发布反馈，后续调用排除已反馈项 |

本期抽取的是可复用的数据语义及小型投影逻辑，不提前规定未来 Narration Tool 的全部入参。不要把一整份 `ActionPlanNarrationContext` 固化为未来工具必须接受的对象，也不提前要求 Agent 每次读取完整 PlayerView 或整个模组。

未来迁移时应保留：原文与人物资料的职责区分、事件证据稳定引用、当次安全正文、受众边界、以及先确认结果后表达的顺序。Agent 可以改变每次叙事选用的补充上下文；已提交但尚未反馈的结果则需要进入本次反馈，或在后续运行设计中明确保留为待反馈内容。

“已反馈”应以反馈成功持久化为准，不能因为模型生成过或申报了引用就算完成。当前代码尚不提供完整的多次反馈消费记录，本期不把 `claimed_evidence_refs` 冒充该能力；这一记录及跨等待窗口恢复由 #421 配合已有消息身份实现。

当前新增证据随既有执行记录保存，升级后生成的行动恢复时复用同一批证据，不重新提交规则。升级前已落库的叙事继续回放；旧在途记录缺少新增证据时保持可恢复的兼容口径。本期不自动改写历史叙事或重建全部旧行动的结果差量，这一限制应记录在实施验收中。

后续迁移可以替换固定装配与终局调用时机，继续复用新增证据和输出保留逻辑。本期的内存引擎回归应保留为新的 Agent 链路验收样本。

重点验收场景：

| 场景 | 预期 |
| --- | --- |
| 每个内置模组开场 | 正式原文完整进入模型输入；输入带有同源关键事实清单；人工抽样检查任务、线索和条件覆盖，允许自然改写 |

| 复合行动、多人确认、检定后移动、刷新重试 | 只叙述实际已提交结果，恢复不重复写状态或发布同一反馈 |
